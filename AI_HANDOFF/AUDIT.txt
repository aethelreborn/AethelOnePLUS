# PolyPlus — Session Audit

This is the PolyPlus half of the audit trail. The launcher half lives in the
AethelONE repository, in `AI_HANDOFF/AUDIT.txt`.

Repo: `aethelreborn/AethelOnePLUS` (fork of `Polyfrost/PolyPlus`).
Remote in this checkout: `origin` → the fork. Never push to `Polyfrost/PolyPlus`.
CI: `Build with Gradle` (`.github/workflows/build.yml`) builds all ten game
versions on every push and republishes the rolling `continuous` release.
`Sync upstream PolyPlus` rebases onto `Polyfrost/PolyPlus` every 30 minutes.

Rules of engagement for this repo:

- No local build. The machine has 3.4 GB of RAM, two cores and no JDK, so
  Gradle cannot run here. Push and watch CI: green is the only verification.
- One push, one full ten-version build. Keep the diff small enough to review.
- `deps.polydium = "1.1.2"` stays pinned: it is the newest version the
  Polyfrost repository serves.
- The version lives in `stonecutter.properties.toml` (`mod.version`) and the
  changelog in `CHANGELOG.md`; both move together.

## 2026-10-21 — The client finally looks after the machine it runs on (1.3.11)

The complaint: the client is supposed to be fast, and on a weak laptop it gives
two or three frames per second. The perf mixins had already been moved out of
PolyPlus into Polydium upstream (`ca60a2e` "move all performance stuff out of
polyplus"), so PolyPlus shipped no performance code of its own and nothing in it
looked at the machine at all. Worse, PolyPlus forced the frame rate to 260 FPS
with vsync off, which is the fastest thing you can do to a laptop: the
processor and the graphics card throttle themselves within minutes.

Seven waves, each green on all ten game versions (1.8.9, 1.21.1, 1.21.4, 1.21.5,
1.21.8, 1.21.10, 1.21.11, 26.1, 26.2, 26.3) with the rolling release published
after every push.
1. `31198fe` **feat(performance)** — a new OneConfig performance page
   (`polyplus-performance.json`, `Category.PERFORMANCE`):
   - *Low-End Mode*: frame cap 60, render distance 6, simulation distance 5,
     particles decreased, entity shadows off, mipmaps off, graphics fast, motion
     blur off. Every value it changes is saved and put back when it is turned
     off.
   - *Adaptive Performance*: caps the game at 30 FPS while the frame rate stays
     low and hands the cap back when it recovers.
   - *Performance report*: names what holds the frame rate back — a renderer
     that draws on the processor (llvmpipe, lavapipe, SwiftShader, the
     Microsoft basic driver), an uncapped frame rate, and the Vulkan backend.
   - Vanilla options are read and written through reflection
   (`client/utils/VanillaOptions.kt`) because 1.8.9 keeps plain fields while the
   modern versions hand out option accessors; an option a version does not have
   is skipped instead of failing.

2. `e6fc230` **feat(performance)** — the main menu stops asking for frames the
   machine cannot deliver: `MainMenuPerformance` walks the menu cap down the
   ladder 120/60/30/20/15 when the menu cannot reach it and back up when it
   can, and the 3D player preview is drawn at 30 frames a second instead of
   once per menu frame.

3. `a6582c3` **feat(performance)** — a frame rate cap in the performance page
   (the monitor refresh rate, 120, 60 or 30). It only touches the video options
   once it has been picked by hand, so a cap set in the vanilla options keeps
   working.

4. `52f6bb0` **fix(performance)** — Polydium puts the game on Vulkan by itself
   when it sees a discrete graphics card, which is what a gaming laptop has.
   When that driver falls back to the processor the game runs at a couple of
   frames per second and there was no way back from inside the game. The
   performance report now offers to switch the game back to OpenGL, and Polydium
   is told as well (`polydium/graphics-api` and `polydium/auto-vulkan` in the
   game folder) so the next launch does not flip it back.

5. `/polyplus performance` prints the frame rate, the frame rate cap, the renderer,
   the graphics backend, the bundled performance mod and everything that holds the
   frame rate back, so the report can be asked for instead of waited for.

6. `3a86519` **feat(performance)** — the performance report names the bundled
   performance mod and the version of it that is running, because Polydium is a
   mod of its own and the report should say whether it is there.

7. `a4c76cf` **feat(performance)** — the report also comes from the main menu,
   which is where a slow machine usually shows itself first, and it says where
   the frame rate was measured.

8. `39bbff9` **feat(menu)** — a more page on the main menu. The account
   switcher, the hosting button, the social menu and the cosmetics sat in a
   column on the right, next to the OneClient logo, and the row of mod buttons at
   the bottom could run into the buttons under the logo. They live on a more page
   now, the more page covers the whole menu so nothing can sit on the logo while
   it is open, and the centre column always keeps the space the mod buttons
   need.

9. Launcher side, `aethelreborn/AethelONE` `e2309c80` **feat(packages)** — the
   launcher asked Modrinth for the newest PolyPlus release, and that release
   never carries the patched build, so a browser-installed PolyPlus stayed on
   whatever version it was installed with while the mirror kept publishing newer
   ones. The mirror manifest decides now: the newest build for the instance's
   game version is offered as a normal mod update, it is applied with the
   launcher's own auto-update mode before a launch, and the patched jar is the
   one that lands in the instance. An older mirror build never replaces a newer
   install and an unreachable manifest leaves the installed mod alone. Shipped in
   AethelONE 2.31.0.

10. `21c6282` **fix(performance)** — the video options belong to the launcher.
    The launcher writes the video settings into the game's own `options.txt`
    before every launch, and the performance settings wrote their own lowered
    values back on top of that, so the two of us could overwrite each other.
    The performance settings now only change the values in memory: the low-end
    mode and the frame rate cap re-apply from the PolyPlus settings on every
    start and the file stays the launcher's alone. The two places that still
    save the options write back exactly what the game read: the graphics backend
    switch and the wWaypoints keybinds it unbound.

Working with the other session (the AethelONE launcher one) on 2026-10-22: the
two repos write the same game's video settings from both sides, so the rule is
now written down on both sides - `options.txt` is the launcher's, the mod only
ever changes the values in memory. Polydium is not on Modrinth (the search
returns nothing), so it cannot be a mod of its own in the launcher's
performance set: it ships inside the PolyPlus jar, and the launcher points at
the patched jar through the mirror manifest.

What Polydium is, since it is asked about: the Polyfrost performance mod, a
separate mod (`org.polyfrost:polydium`) that PolyPlus bundles inside its jar.
It carries the mixins that skip work the vanilla renderer does not need, and on
1.21.11 and newer it can draw through Vulkan. The low-end mode also turns
Polydium's section cache off, because that copy of the built chunk sections is
memory a weak machine cannot spare.

LESSON: a client that bundles a performance mod still has to look after the
machine, because the bundled mod only knows how to draw faster, not that the
machine is drawing on the processor or that an uncapped frame rate is what makes
a laptop throttle itself into single digits. A bad frame rate has a reason, and
naming it (software renderer, uncapped, the wrong graphics backend) is worth
more than any optimisation that hides it.

LESSON: Polydium's early Vulkan switch is invisible from inside the game and
it is the first thing to check on a laptop that suddenly runs at a couple of
frames per second. A broken Vulkan driver on a discrete graphics card is the
difference between a playable game and an unplayable one, and the fix is one
file in the game folder.

LESSON: an option that only applies once the user picks it by hand must not
write anything on every launch, or it silently overwrites a setting the user
made somewhere else. The frame rate cap keeps a flag for that reason.

## 2026-10-22 - The upstream sync needs a port, not a rebase

The "Sync upstream PolyPlus" workflow keeps failing on the rebase, and the
reason is not a stale patch. Polyfrost merged `feat/wardrobe` upstream and it
rebuilt the cosmetics screen, the emote wheel, the previews and the social UI:
40 commits and a new `client/gui/wardrobe/` package. Our 84 patches after the
common base `c433d5d` are written against the old structure, and about thirty
of them touch files upstream rewrote.

The first conflict says it all: `a385ab1` (pets folded into the Shoulder tab)
against the new `WardrobeShell`/`WardrobeStoreData` structure. Upstream keeps
Pet as its own tab, so that feature is ours and has to be re-implemented, not
dropped. The same applies to the wardrobe search and the All rail tab
(`b12f7b8`), the store purchase fix (`d2ff7c4`), the badge on the scoreboard
and on the friends list, the social mute and presence work, the emote wheel
fallbacks, the config options and the preview renderer.

So this is a port of our features onto the new wardrobe, not a mechanical
conflict resolution. Doing it in one pass risks silently dropping features the
owner asked for (the pet shoulder tab, the scoreboard badge, the wardrobe
search), so the fork stays on the old base for now: it builds, it is released,
and the only red thing is the scheduled sync, which has failed the same way for
days.

The plan for whoever takes it on:

1. Branch from `upstream/main` (`7cc0f9c`) and replay our patches in order.
2. For every patch whose file upstream rewrote, decide per feature whether
   upstream carried it over. The wardrobe rewrite covers a lot of it (outfits,
   skins, variant swatches, previewing the selected item).
3. Re-implement what upstream did not carry over as fresh commits against the
   new structure and drop the old patch.
4. Push it and let the sync workflow confirm the result is green.

The launcher side is not part of this: the two repos only meet at the game's
video settings, and that is settled - the launcher's `options.txt`, the mod's
values in memory.

## 2026-10-22 - The upstream port is done, and the cosmetics live again

The merge is in. `feature/upstream-merge` was merged into `main`, and every one
of the ten game versions builds again (1.8.9 through 26.3).

What it took:

- The conflicts were resolved per file, and where both sides had something to
  say, both sides stayed: our performance page, the more page, the host-world
  keybind, the local-backend hint, the wing visibility option and the pet
  preview work stayed, and upstream's wardrobe, the wardrobe keybind, the forced
  capes and the outdated-runtime message came with it.
- OneConfig 1.5.0 took the theme and the icon out of the internal package, so
  the two files that still used the internal one were moved over to the public
  API, and the shape helpers are read-only composables again.
- Upstream rewrote the social primitives and took the badge-aware player name
  with it, so the badge atlas, the glyph and the player name went back into the
  friends list and the sidebar.
- The pets are folded into the Shoulder section of the new wardrobe, and the
  emote wheel says that there are no emotes to use instead of showing an empty
  ring.
- `deps.polydium` stays at 1.1.2: the Polyfrost repository serves 1.1.2 and
  1.1.5 is a 404 there, so upstream's own pin does not resolve.

What was left behind on purpose: the wardrobe search and the All rail tab
(upstream's wardrobe has a search of its own), the list fallback for more than
eight owned emotes (the wheel holds a fixed set of slots now) and the
pick-up-after-purchase fix (upstream's store refetches when a purchase lands).

LESSON: when an upstream project rewrites the screen a feature lives on, the
feature has to be re-implemented against the new structure - a hunk resolution
would have dropped the pet shoulder tab, the scoreboard badge and the presence
badge in the social lists, and nobody would have noticed until the cosmetics
were gone.

### The OneConfig 1.5.0 catch (both repos)

PolyPlus 1.3.12 needs OneConfig 1.5.0 (upstream moved the theme and the icon
into the public package in 1.5.0 and the new wardrobe uses them). OneConfig
1.5.0 is **not on Modrinth** (the newest there is 1.4.4) and **not on CurseForge**
(two files from 2021) - it only exists on the Polyfrost maven. The bundles the
launcher installs ship `OneConfig-1.21.1-fabric-1.4.4.jar`, so an instance on
1.4.4 would have skipped PolyPlus 1.3.12 entirely: Fabric refuses a mod whose
`oneconfigv1` requirement is not met, and the game would start without
PolyPlus - the namebadge patch and the cosmetics gone.

So the auto-update could have made the mod disappear. Two guards:

- The mirror manifest carries the OneConfig version each build needs
  (`oneconfig: "1.5.0"`), and the launcher's update check reads it: when the
  providers do not carry a OneConfig new enough for the build, the PolyPlus
  update is not offered and the instance keeps what it has.
- The launcher can fetch OneConfig 1.5.0 from the Polyfrost maven
  (`https://repo.polyfrost.org/releases/org/polyfrost/oneconfig/<mc>-fabric/1.5.0/`),
  which is the other session's side of it.

This is not only our problem: upstream PolyPlus on its main branch needs
OneConfig 1.5.0 too, so whoever owns OneConfig has to publish it to Modrinth
before the new wardrobe can reach launcher users at all.
